STUDY NOTE · CONTEXT ENGINEERING

Learning while you sleep: beyond memory to dreaming

Lamis Mukta (Anthropic, Applied AI) · AI Native DevCon, June 2026 · 31m 52s · Original video
THE ONE-LINE TAKEAWAY

Model intelligence alone doesn't compound in your organization — the context you curate around it does, which is why memory is the multiplier on every model upgrade.

But memory written in-band, by the agent doing the task, hits a hard ceiling: it competes for the same tokens as the work, and it can only see one session. Dreaming — a batch, out-of-band process that reads many transcripts against the memory store and proposes changes — is what closes the continual-learning loop.

01 The starting frame

Why context, not intelligence, is the lever 0:30–3:14

The talk opens on a joke that doubles as the thesis — "I hope that your context windows are not too full and you have a bit of space for a little bit more information about context." The speaker's seat is the Applied AI team at Anthropic, sitting between research, product and go-to-market, working with startups pushing "right up against the boundary of what is possible with models and products today."

What new models give you

Raw intelligence, released on a cadence, identical for everyone. It arrives knowing nothing about your codebase, your organization, or your preferences.

What context engineering gives you

The task- and org-specific knowledge that is orthogonal to model intelligence — and therefore multiplies it, again, every time a smarter model ships.

The failure symptoms are familiar: agents not knowing their way around a codebase, not knowing user preferences, and — the one that stings — not being better at a task the second time they do it. No learning from mistakes means no continual learning.

02 Glossary

The terms the talk uses as given

Context engineering

The work of getting the right task-, user- and organization-specific information in front of the model, as distinct from making the model itself smarter.

Point — framed as an investment, not a fix: because it's orthogonal to intelligence, it keeps multiplying as models improve rather than being obsoleted by them.

CLAUDE.md

A plain markdown file injected at the start of a session with instructions about the codebase, the organization, and user preferences. Shipped with Claude Code.

In her words — "unreasonably effective." Both human and agent can read and write it. Its failure mode is context bloat as the file grows.

Memory tools

Tools that let agents autonomously decide when to read, write and update their own memories, during a session.

Point — the finding was that autonomy works. The subsequent direction was to become less opinionated about what the tools look like, not more.

Skills & progressive disclosure

A file whose front matter — a couple of sentences at the top — is all the agent reads before deciding to load it. Detail lives in the body and costs nothing until loaded. Good for procedural workflows you have an opinion about, end to end.

Her analogy — a bookshelf in your room. You scan the titles as someone talks to you and pull one down when it's relevant. "If someone walked up to me and started speaking to me in French and I noticed that I have a French dictionary, I could pull that out" — without seven years of French classes already loaded into your context.

Memory as a file system — current best practice

Model the memory store as a directory of markdown files. Don't prescribe special read/write tools — agents are already very good at bash and grep. Index it well so search over it does the job progressive disclosure did for skills.

The three rules — markdown for reading; let memories grow large but give agents tools to index and search them; give agents autonomy when writing.

In-band vs. out-of-band memory

In-band: the agent reads and writes memory inside the session where it's doing the task. Out-of-band: a separate process, with its own resources, curates memory outside any task session.

Point — this distinction is the hinge of the whole talk. Everything before it is in-band; dreaming is the out-of-band half.

Dreaming

"A second-order process over memory" — a batch, asynchronous job with its own allocated token budget, whose only job is to make sure the memories themselves are effective and up to date.

The three layers — context (what agents reference) → memory processes (agents curating it themselves) → dreaming (a process curating the curation).

Hashing — the concurrency mechanism

Before drafting an edit the agent takes a hash of the memory; before committing it takes another. If they differ, someone else wrote in the meantime and the write is refused — the agent re-pulls, re-drafts, and tries again.

Point — this is optimistic concurrency control, named as ordinary engineering practice rather than as anything AI-specific. That framing comes back in the Q&A.

Stale memory

Something true in the past that isn't now, something written incorrectly, or something injected maliciously by a prompt injection aimed at your memory store.

Point — she flags this twice, and the second time as the limitation she'd forgotten to list: nothing in an in-band system owns the job of re-checking what's already written.

Intelligence alone doesn't compound 2:24–3:14

A newer model doesn't know what it takes to succeed in your organization. Because that knowledge is orthogonal to intelligence, investing in it multiplies every future model rather than being replaced by one.

"the intelligence alone is not going to compound because they need this context that helps them perform the specific tasks that you need them to."

One year, four steps, each one simple 3:37–8:18

CLAUDE.md → memory tools → skills → the file system. Each stage was the dumbest thing that could work, shipped, then pushed until its ceiling showed: bloat for CLAUDE.md, human opinion-forming for skills. The endpoint wasn't designed, it was arrived at.

"At Anthropic, we like to say do the simple thing that works."
3

The neat idea breaks in production 8:53–10:23

Build the file-system memory as described and it works — you feel the continual learning. Then scale it: many agents writing at once, long runs, complicated codebases. Two agents write the same file. One agent hits a problem and edits the organization-wide context every other agent reads from. Humans and agents edit the same store with no shared record of who changed what.

"if something was incorrect there, that would scale to all of your agents and be pretty disastrous."
4

Four guardrails make autonomy deployable 10:27–13:46

Not restrictions on the agent's creativity — the conditions under which that creativity can be shipped.

GuardrailWhat it has to answer
VersioningCan I roll back a bad update? Which session and transcript produced it? Which agent or human made it?
ConcurrencyHash before drafting, hash before committing; mismatch means re-pull, re-draft, retry.
PermissioningOrg-wide curated knowledge read-only; an agent's own scratchpad writable; team- and cross-section scopes in between.
PortabilityA clean API, so context you spent real effort curating is reachable from multiple product surfaces and systems.
5

What you get when it holds 14:06–15:15

Accuracy first: the second run of a task goes better because the agent noted what went wrong. That produces a second-order effect on cost and speed — fewer tokens, more one-shots, because the agent actually knows what it's doing. And the humans get their own capacity back.

"frees up capacity and context for you as product developers potentially to focus on product wins while you know that the agents are doing this kind of self-learning, continual learning loop in the background."
6

The new bottleneck is in-band itself 15:19–17:04

Two structural limits, neither fixable by better prompting. Split focus: you're asking one agent both to finish the task and to invest in memory that only helps a future run — an optimization problem with no clean answer, plus latency. Visibility: an agent sees only its own session, so cross-session patterns are invisible to it.

"when you get frustrated that your agent keeps making the same mistake over sessions, it just doesn't understand how frustrating that is, because it has a new context window in each of those."
7

The school analogy supplies the shape of the fix 17:04–18:06

Students submit work; teachers mark it; a head teacher reviews everything. We built that structure in the real world for two reasons — some people have dedicated capacity for helping others learn, and some have visibility over the whole cohort, enough to spot a pattern and change the curriculum. Both are exactly what the in-band agent lacks.

"as always, we kind of look to the real world to think about how to build these systems."
8

Dreaming, mechanically 18:10–23:45

Take the existing memory store plus a batch of session transcripts. An orchestrator deploys a fleet of sub-agents to analyze the transcripts, reviews their responses, decides which patterns are prevalent enough to warrant a change, and outputs a proposed new memory store — each proposal carrying example transcripts and prevalence stats as its evidence. A human accepts or rejects. Crucially, the transcripts include tool calls and metadata, not just the message passes.

"the agent is able to … spend tokens on solving this problem of making agents learn better."

The head teacher, made concrete: every geography student answers one question with garbage → the topic is missing from the curriculum. Every maths answer is wrong the same way → everyone's calculator is in radians, so publish the calculator setting; in agent terms, a tool is misconfigured and the transcripts show the same call failing. Everyone in the fleet is using too many em dashes → that's an organization-wide context change.

04 Principles worth taking out of the room

What generalizes past this talk

① The upgrade everyone gets is not the one that compounds

A model release lands identically for you and your competitor. The only part that accumulates is the part you curated — which is why work that looks orthogonal to the frontier is the work that survives it. Ask of any investment: does a vendor's next release replace this, or multiply it?

② Ship the simple thing to find where it breaks

Four stages in a year, each one a plain file, each one adopted until its specific ceiling appeared. The ceiling is information you cannot get by designing harder up front — you get it by shipping the naive version and watching which way it fails.

③ Autonomy scales on an audit trail, not on a shorter leash

Versioning, hashing and permissioning don't constrain what the agent may invent; they make what it invents reversible, attributable and blast-radius-bounded. The way to grant more freedom is to make mistakes cheaper to undo, not to narrow the range of possible mistakes.

④ Whoever does the work is the wrong one to grade it

Asking one actor to both complete a task and invest in future performance sets those goals competing for the same budget, and the immediate task will usually win. Learning needs capacity that is allocated separately and cannot be raided by the work — that's what a teacher is, and what dreaming is.

⑤ A recurring failure is invisible at the level where it recurs

The agent repeating a mistake across sessions is not ignoring the pattern; it has never seen two instances at once. Any pattern that lives above the unit of work has to be reviewed above the unit of work — otherwise the fleet keeps making a mistake nobody in it is positioned to notice.

⑥ Converging back on old engineering is a sign of maturity, not failure

Asked whether versioning and concurrency mean reinventing databases from first principles, she agrees and reframes: you start by letting agents commit whatever they like, learn which primitives actually work, then codify those into the harness. Reaching for the boring, deterministic solution is what having enough signal looks like.

05 To check, to build, to watch

The talk's open items and thresholds

  • Start in-band; the threshold to go further is stated. CLAUDE.md, skills, and autonomous memory management "goes a really long way." Add production guardrails when you hit: many agents at once, agents running over long periods, a workspace or codebase you keep developing over time, or very complex domains.
  • Audit your memory design against the four guardrails. Versioning (rollback + originating session + author), concurrency (hash before and after), permissioning (org-wide read-only, scratchpad writable), portability (clean API). Her word for the goal: "safe, verifiable, auditable."
  • Decide who owns staleness. In a purely in-band system nothing re-checks what's already written — and stale includes maliciously injected. If you're not building dreaming yet, name the process that does this instead.
  • Feed dreaming the tool calls, not just the conversation. The radians-vs-degrees example only surfaces if the transcripts carry tool calls, skills used, and metadata.
  • Steering is a design surface. The agents that write and coordinate dreaming can be told what counts as important and what doesn't, which is where the process gets tuned to your organization.
  • Permissions and dreaming compose — if you configure them to. Asked how dreaming respects hundreds of different permission sets: you choose exactly which session transcripts to attach. A time-window job takes everything; instead, select transcripts whose permission set matches the memory store.
  • Off-the-shelf, per her answer: the versioning and hashing described are available through the memory and dreaming API in Claude Managed Agents. (Asked directly for an enterprise implementation; she noted she'd been "coy in the talk because we're not allowed to make product calls to action.")
  • Not a coding-only practice. She uses memory for building presentations — how she likes things written, how she likes her slides — and it develops over time.
  • The cost objection, answered. Dedicated token spend for dreaming sounds expensive; the counter is that better memory drives cost down through more one-shot completions and fewer wasted tokens. Worth measuring for yourself rather than assuming either direction.
